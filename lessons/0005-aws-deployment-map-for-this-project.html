Lesson 0005 · Deployment map

AWS deployment is your Docker Compose file split into managed services.

You already have the application pieces locally: API, worker, Redis, PostgreSQL, S3-style media storage, and secrets. AWS gives each piece a production home.

Local piece to AWS service

Current project pieceAWS production homeWhy
FastAPI web/API container Amazon ECS service Runs the API as a managed container service.
RQ worker container Amazon ECS worker service Runs background inspections separately from web requests.
PostgreSQL container Amazon RDS for PostgreSQL Managed backups, storage, availability, and database operations.
Redis container Amazon ElastiCache for Redis/Valkey Managed cache/queue infrastructure for progress, rate limits, and RQ.
Local uploads folder Amazon S3 Durable object storage for inspection images/videos.
.env secrets AWS Secrets Manager Keeps API keys and database credentials out of images and source code.

The important production split

Stateless containers

The API and worker should be replaceable. If a container dies, another one can start without losing uploaded media or run history.

Stateful managed services

PostgreSQL, Redis, and S3 hold state. AWS manages their durability, networking, scaling options, and backups.

What changes in the app?

Ideally, very little application code changes. Most deployment movement happens through environment variables:

DATABASE_URL=postgresql://...
REDIS_URL=redis://...
MEDIA_STORAGE_BACKEND=s3
AWS_S3_MEDIA_BUCKET=...
AWS_REGION=...
OPENAI_API_KEY=...

The same FastAPI and RQ code can run locally or in AWS because the service locations are config, not hard-coded logic.

What you should not deploy first

Do not try to move everything at once. The safest sequence for this project is:

  1. S3 media storage.
  2. RDS PostgreSQL.
  3. ElastiCache Redis.
  4. ECS API and worker.
  5. Secrets Manager and tighter IAM roles.

This order moves durable state first, then compute.

Retrieval practice

Question: Why should uploaded inspection images live in S3 instead of inside the API container?

Show answer

Because containers are replaceable compute. If the container restarts, scales, or is redeployed, local files can disappear. S3 is durable object storage designed for files.

Lesson 0006 · Request lifecycle

A production inspection run is a handoff chain, not one giant request.

The browser starts the run, but S3, PostgreSQL, Redis/RQ, and the worker each own a different part. This keeps long AI workflows durable and resumable.

The corrected workflow

  1. User submits request. The browser sends asset info, inspection notes, runtime settings, and media files to FastAPI.
  2. API stores media in S3. S3 stores image/video bytes. The API stores the S3 bucket/key metadata in PostgreSQL.
  3. API stores the run record in PostgreSQL. PostgreSQL becomes the durable source of truth for run status, asset info, prompt/notes, media references, and settings.
  4. API enqueues a lightweight RQ job in Redis. The job should usually contain only a run_id, not the full image or full request.
  5. Worker picks up the job. The worker loads the request from PostgreSQL and downloads the media from S3 when needed.
  6. Worker runs the agent graph. Evidence, severity, RAG, maintenance planning, scheduling, and report tools run in sequence with checkpoints/idempotency.
  7. Worker writes results to PostgreSQL. Progress, tool runs, final report JSON, rendered report, artifacts, and review status are persisted.
  8. API serves progress and results. The UI polls the API, and the API reads PostgreSQL/Redis/S3-backed records to show the current state.

Who owns what?

ThingOwnerReason
Image/video bytes S3 Durable object storage. Containers can restart without losing uploaded media.
User prompt, notes, asset, settings PostgreSQL/RDS Structured, queryable, durable application state.
Queued work Redis/ElastiCache + RQ Fast temporary coordination between API and worker.
Long-running execution RQ worker on ECS/EC2 Keeps AI workflow outside the web request timeout path.
Final report and audit trail PostgreSQL/RDS, with S3 for file artifacts Database stores records; S3 stores larger generated files if needed.

The common mistake

Do not put the whole request into Redis as the only copy. Redis is excellent for queues, cache, progress, and rate limits, but PostgreSQL should hold the durable inspection record.

A good RQ payload looks like this:

{
  "run_id": "run_178...",
  "attempt": 1
}

The worker uses run_id to load everything else from PostgreSQL.

What happens if something crashes?

API crashes after S3 upload

The media is safe in S3. The run can be marked failed or retried if the DB record exists.

Worker crashes mid-graph

RQ retries the job. Tool-level idempotency and checkpoints prevent duplicate durable writes where possible.

Redis loses a queue item

PostgreSQL still has the run record. A reconciliation job can find stuck queued/running runs and re-enqueue them.

S3 object is missing

The worker should fail clearly, write an error to PostgreSQL, and show the UI that evidence retrieval failed.

Retrieval practice

Question: Why should the RQ job contain run_id instead of the uploaded image bytes?

Show answer

Because Redis should coordinate work, not become the durable file store. The image belongs in S3, while PostgreSQL stores the run and media reference.

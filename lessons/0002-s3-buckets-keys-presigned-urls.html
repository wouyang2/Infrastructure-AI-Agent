Lesson 0002 · S3 for inspection media

S3 stores objects. Your database stores what those objects mean.

In your app, an uploaded bridge image is not just a file. It is evidence attached to an inspection run. S3 should hold the bytes; PostgreSQL should hold the identity, ownership, checksum, and workflow meaning.

The three S3 words you need first

Bucket

A top-level container for objects. Example: infra-agent-media-dev. Treat it like the storage boundary for an environment.

Object

The stored file plus its metadata. Example: a JPEG image, an MP4 video, a generated PDF, or an annotated image.

Key

The object’s path-like name inside the bucket. Example: inspections/run_123/original/bridge.png.

Map this to your current upload

Today your app saves an uploaded image like this:

artifacts/uploads/bridge-spalling_a04bc7ca35.png

In S3, the production version would look more like this:

bucket = infra-agent-media-dev
key    = inspections/run_1785/original/media_abc123-bridge-spalling.png
url    = s3://infra-agent-media-dev/inspections/run_1785/original/media_abc123-bridge-spalling.png

The SQL row would keep the stable application facts:

media_id = media_abc123
run_id = run_1785
storage_backend = s3
storage_key = inspections/run_1785/original/media_abc123-bridge-spalling.png
checksum_sha256 = ...
scan_status = clean

Why not make the S3 bucket public?

Inspection media can be sensitive. A public bucket is the wrong default. Instead, keep the bucket private and let the API create presigned URLs.

Upload path: Browser asks FastAPI for permission to upload one object.
FastAPI checks identity: Is this user allowed to upload evidence for this case?
FastAPI creates presigned PUT URL: Temporary permission to upload exactly one object key.
Browser uploads to S3: The large file does not need to pass through your API worker.
FastAPI records metadata: SQL stores media ID, run ID, key, size, checksum, and scan status.

Retrieval practice

Answer before opening the answer. This is the one pattern to remember.

Question: Your app has this media row:

media_id = media_9
run_id = run_42
storage_backend = s3
storage_key = inspections/run_42/original/media_9-crack.png

What is probably stored in S3, and what is stored in PostgreSQL?

Show answer

S3 stores: the actual bytes of media_9-crack.png, addressed by the bucket plus object key.

PostgreSQL stores: the media row: media_id, run_id, storage backend, storage key, checksum, size, MIME type, scan status, and case linkage.

Implementation direction for this project

Your current code already has the right stepping stone: inspection_media. The next implementation would be a storage abstraction:

MediaStorage
  LocalMediaStorage   -> artifacts/uploads
  S3MediaStorage      -> AWS S3 bucket
  MinioMediaStorage   -> local S3-compatible dev bucket

That lets the Evidence Agent and UI ask for media by metadata instead of caring whether bytes live on disk or S3.

Lesson 0003 · IAM for S3

IAM answers one question: what is this app allowed to do?

Once your app can upload to S3, the dangerous part is permission. IAM lets you give the app only the actions and resources it actually needs.

IAM in one minute

Identity

Who or what is calling AWS. In production this should usually be an IAM role attached to the running service.

Policy

A JSON permission document. It says which actions are allowed on which resources.

Action

The operation. For this project: s3:PutObject, s3:GetObject, and maybe s3:DeleteObject.

Resource

The specific AWS thing. For this project: one bucket prefix, not every bucket in the account.

Bad permission vs better permission

Too broad:

Action: "s3:*"
Resource: "*"

This says: the app can do anything to any S3 resource. That is far more power than an inspection API needs.

Better:

Action:
  - "s3:PutObject"
  - "s3:GetObject"
Resource:
  - "arn:aws:s3:::infra-agent-media-dev/inspection-media/*"

This says: the app can upload and read only media objects under the app’s bucket prefix.

How this maps to your code

The new S3 backend will use environment variables like:

MEDIA_STORAGE_BACKEND=s3
AWS_S3_MEDIA_BUCKET=infra-agent-media-dev
AWS_REGION=us-east-1
AWS_S3_MEDIA_PREFIX=inspection-media

Those settings do not grant permission by themselves. They only tell the app where to store media. IAM decides whether AWS accepts the request.

Retrieval practice

Question: Why is s3:PutObject on one bucket prefix safer than s3:* on *?

Show answer

Because the app can only upload objects where it is supposed to. If the app is compromised or buggy, it cannot list, delete, or modify unrelated S3 buckets and objects across the account.

Implementation note

Local development can use AWS CLI credentials or environment variables. Production should use IAM roles attached to the service running the API/worker. The role gets the policy, not the source code.
